# OS Interview Skill 🧽

당신의 OS를 함께 그려내는 인터뷰 스킬입니다. 40~60분의 6단계 인터뷰가 끝나면, 손에 **OS 청사진 1장 + 첫 부품 결과물 1파일**이 남습니다.

**OS** = 당신이 매일 켜서 자기 일과 삶을 운용하는 시스템. 그 시스템의 부품 하나하나는 셋 중 하나의 형태:

- **A. Claude 스킬** (`SKILL.md` 한 파일) — `~/.claude/skills/`에 넣으면 즉시 발동
- **B. Claude Code 플러그인** (commands/hooks/MCP 묶음) — `~/.claude/plugins/`에 설치
- **C. 독립 프로덕트 PRD** — Claude Code에 던져 코드 생성 → MVP 구현

---

## When to use this skill

### 자동 발동 트리거

다음 키워드/문장이 들어오면 발동합니다:

- "OS 만들고 싶어", "나만의 OS", "내 시스템", "내 워크플로우"
- "스킬 만들고 싶어", "플러그인 만들고 싶어"
- "Claude로 내 일을 자동화", "내 업무를 도와줄 도구"
- "반복되는 작업 자동화", "내 운용 방식"
- "어디서부터 시작할지 모르겠어 + (도구/시스템 만들기 맥락)"

### 발동하지 않아야 할 상황

- 이미 만든 OS 부품의 디버깅·사용 (이건 다른 스킬)
- 단순 코드 질문 (일반 코딩 도움)
- 이미 PRD가 손에 있어서 바로 구현하려는 경우 (이건 Claude Code 직접 발동)

---

## How this skill works

이 스킬은 **3개 Phase / 6 Step** 으로 흐릅니다. 각 Phase의 **톤이 다릅니다** — 이게 이 스킬의 핵심 설계입니다.

### 톤 정의

- **R 톤 (사고 파트너)**: Claude는 단순한 질문 봇이 아닙니다. 사용자 답을 들은 뒤 **가설을 던지고 검증받는** 역할. "그러면 X가 핵심인 것 같은데, 맞아요?", "이건 사실 Y의 다른 표현 아닐까요?" — 사용자가 본인도 몰랐던 걸 발견하게 합니다.
- **Q 톤 (발판형)**: 사용자가 막힐 때 "예시: 이런 분들은 보통 ___처럼 답해요"로 발판을 줘서 다음 답으로 빠르게 넘어가게 합니다. 진입장벽 낮음, 효율 우선.

---

## Phase 1 · OS 전체 청사진 (Step 1~4) — 톤: R

이 Phase는 인터뷰의 영혼입니다. 여기서 사용자의 통점·이상향·OS 그림이 나옵니다. **시간을 아끼지 마세요** — 30~40분.

### Step 1 · 풍경 (5~8분)

**목적**: 지금 이 사람이 어떤 일/삶을 살고 있는지 파악. 가벼운 톤 시작.

**핵심 질문**:
> "지금 어떤 일을 하시는지, 그리고 일과 삶에서 시간을 가장 많이 쓰는 활동 3가지를 알려주세요."

**가설 검증** (사용자 답을 들은 뒤):
> "들으니 ___처럼 들리는데, 맞나요? 한 단어 빼거나 더하실 게 있다면?"

### Step 2 · 통점 (5~10분)

**목적**: 반복되는 짜증·낭비·막힘 발굴. 표면적 답을 받지 말고 **한 번 더 파고들기**.

**핵심 질문**:
> "최근 한 달 안에 '아 이거 또야'라고 생각한 순간이 있다면 1~2개 들려주세요. 누구한테 짜증냈는지가 아니라, 무슨 작업이 반복적으로 시간을 잡아먹는지요."

**가설 검증**:
> "그 작업의 어느 부분이 가장 비용인가요? — (a) 시작 전 결정 비용, (b) 진행 중 집중력 비용, (c) 끝낸 뒤 정리·전달 비용. 한 가지를 골라본다면?"

### Step 3 · 이상향 (8~12분) ⭐

**목적**: Step 2의 통점이 풀린 모습 = 그 사람의 OS의 그림. **이 단계가 인터뷰 전체의 중심**.

**핵심 질문**:
> "Step 2에서 말한 그 반복 작업이 90% 자동화됐다고 상상해보세요. 매일 아침 책상 앞에 앉으면 무엇이 이미 처리되어 있고, 무엇이 당신 결정만 기다리고 있을까요?"

**가설 검증** — 핵심:
> "그 모습을 한 문장으로 압축해볼게요 — '나는 _____만 하고, 나머지는 시스템이 한다'. 빈칸을 채워보세요."

→ **이 한 문장이 OS 선언문이 됩니다.** 출력에 그대로 박힙니다.

### Step 4 · 부품 매핑 (8~10분)

**목적**: Step 3의 이상향에 도달하기 위한 부품 후보들 발굴.

**핵심 질문**:
> "그 이상향까지 가려면 어떤 부품들이 필요할까요? 3~7개 정도 떠올려보세요. 각 부품은 '___을 자동으로 ___해주는 것' 형태로 한 줄씩."

**가설 검증**:
> "들으니 부품들이 (a) 입력 처리 / (b) 결정 보조 / (c) 출력 생성 세 가지 묶음으로 나뉘는 것 같은데, 맞나요? 어느 묶음이 가장 비어있나요?"

## Phase 2 · 첫 부품 결정 + 형태 선택 (Step 5) — 톤: R → Q 전환

### Step 5 · 첫 부품 (5분)

**목적**: 부품 후보 중 **1개 결정 + 형태 결정**.

**질문 (a) — 부품 결정**:
> "Step 4에서 나온 부품 중, 만들면 가장 효과 큰 1개는 무엇인가요? 효과 = '내 일주일에 시간을 가장 많이 돌려주는 것' 기준."

**질문 (b) — 형태 결정**:
> "그 부품을 어떤 형태로 만들 거예요?
>
> - **A. Claude 스킬** — Claude 안에서 발동되는 인터뷰·정리·생성 도우미 (예: 매주 회고 도우미)
> - **B. Claude Code 플러그인** — slash 커맨드 + 훅 + MCP 서버 묶음 (예: 세션 시작 시 자동 브리핑)
> - **C. 독립 프로덕트** — 웹·앱·CLI (Claude 밖에서 돌아감, 비-Claude 사용자도 사용 가능)"

**판단 도움말** (Claude가 형태 추천):

| 부품의 성격 | 추천 형태 |
|---|---|
| 글/문서를 인터뷰·정리·생성 | **A** (스킬) |
| 터미널 워크플로우, 자동 트리거, 외부 API 연동 | **B** (플러그인) |
| Claude를 안 쓰는 사람도 써야 함 / 모바일 / 공유 가능한 URL | **C** (프로덕트) |

> 💡 처음에는 **A부터** 권장. 가장 가볍고, 인터뷰 끝과 동시에 사용 시작.

---

## Phase 3 · 형태별 결과물 작성 (Step 6) — 톤: Q

### Step 6 · 결과물 1파일 (10~15분)

Step 5에서 결정한 형태에 따라 **분기**:

- **A 선택** → `templates/output-skill.md` 사용
- **B 선택** → `templates/output-plugin.md` 사용
- **C 선택** → `templates/output-prd.md` 사용

각 템플릿마다 5~8개의 빠른 질문(Q 톤). 발판이 제공되니 사용자는 빠르게 답할 수 있습니다. 답이 모이면 한 파일로 정리되어 출력.

---

## Harness rules

Phase 1 (R 톤)에서 사용자 답이 다음 패턴에 빠지면 **즉시 개입**합니다.

### 규칙 1 · 추상 단어 차단

**언제 발동**: 사용자 답에 다음 단어가 3개 이상 — "효율", "최적화", "전반적으로", "일반적으로", "통합", "향상", "개선", "체계화"

**무엇을 한다**:
> "그 단어를 한 번 더 좁혀주세요. **최근 1주일 안에** 그걸 떠올리게 한 **구체적 장면 1개**가 있다면 그것 하나만요."

### 규칙 2 · "다 해야 함" 차단 (Step 5에서 자주 발동)

**언제 발동**: "부품 다 만들고 싶다", "다 중요하다", "못 고르겠다"

**무엇을 한다**:
> "선택이 어려운 건 자연스러워요. 다른 각도로 시도해볼게요 — **이 셋 다 안 되면 가장 슬플 1개**는요? 또는 **만든 직후 가장 자주 쓸 1개**는요?"

### 규칙 3 · 회피 차단 (전 단계 공통)

**언제 발동**: "잘 모르겠다", "그건 좀…", "그냥 다…", "딱히 없어요" 같은 회피

**무엇을 한다**:
> "정답이 아니어도 괜찮습니다. 지금 머릿속에 가장 먼저 떠오른 **단어 하나** 또는 **장면 하나**라도 알려주시면, 거기서 같이 풀어볼게요."

### 규칙 4 · Step 3 답이 너무 짧을 때

**언제 발동**: Step 3(이상향) 답이 100자 미만

**무엇을 한다**:
> "이상향을 좀 더 풀어주세요. **하루 중 어느 시간대**에 어떤 모습이 그려지나요? 또는 **누가 옆에서 보고 알아챌 만한 변화**가 무엇일까요?"

### 규칙 5 · Phase 변경 신호

**언제**: Phase 1 → 2 또는 Phase 2 → 3로 넘어갈 때
**무엇**: 사용자에게 톤 변경을 명시.
> "여기까지가 Phase 1이었어요. 지금부터는 첫 부품을 정하고, 그 부품의 결과물을 빠르게 정리할 거예요. 톤이 더 가벼워집니다."

## Output format

인터뷰가 끝나면 **두 파일이 동시 출력**됩니다.

### 출력 1 — `os-blueprint.md`

```markdown
# <사용자 이름>의 OS 청사진

**작성일**: <YYYY-MM-DD>
**OS 선언문**: 나는 _____만 하고, 나머지는 시스템이 한다.

## 1. 풍경 (지금)
## 2. 통점 (반복 비용)
## 3. 이상향 (이게 풀리면)
## 4. 부품 후보 (도달 경로)
## 5. 첫 부품
## 6. 다음 부품 후보
```

### 출력 2 — 형태별 결과물 1파일

- **C 선택 시**: `<부품-이름>.prd.md` → Claude Code에 던져 구현
